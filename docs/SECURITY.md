# Security model and checklist

- Provider signatures, Google OIDC and Apple JWS are verified before event IDs or payloads are trusted.
- Firebase ID tokens are checked for revocation on authenticated account APIs.
- PC/Mac sign-in uses a short-lived displayed code plus a separate 256-bit polling secret whose plaintext is never stored. Approval requires a verified, recently authenticated Firebase account; collection is transaction-leased and one-time. Every custom token is bound to a server-side per-account device-session generation, and every protected backend request made with such a token checks the current generation. Revoking sessions, disabling an account, or scheduling deletion deletes outstanding approvals, rotates the generation, records a Firebase-authentication cutoff, and revokes refresh sessions, closing the mint-before-revoke/exchange-after-revoke race. The desktop Firebase client key is served from a Netlify variable at runtime rather than embedded in Git. The bridge validates ID-token issuer/audience and persists only the refresh token inside NW.js per-user app data; polling secrets and custom tokens remain memory-only. See `PC_MAC_DEVICE_SIGN_IN.md`.
- Provider customer, transaction and subscription IDs are immutable to one Firebase UID; conflicting links fail closed.
- Purchase tokens are hashed for identifiers and never returned to other clients. The Google Play subscription token needed for missed-webhook recovery is stored only as AES-256-GCM ciphertext authenticated to its subscription hash and Firebase UID. Its versioned key ring is a Netlify secret, supports overlap during rotation, and is never committed. Final account deletion destroys the ciphertext. Clients cannot write grants or entitlement documents.
- Historical discount proof requires a paid, allowlisted WonderLang desktop Checkout Session and the same Firebase-verified email. The coupon is applied only by the server.
- Checkout Price/Coupon IDs are selected server-side. Client prices, products and entitlement claims are ignored.
- Premium second-mobile-platform requests derive the target solely from effective permanent ownership; the client never chooses the platform or creates the grant. Approval uses an expiring transaction lease, a deterministic administrator grant ID and an immutable audit ID. Customer responses omit support reasons, administrator identities, lease tokens and internal grant IDs; account deletion removes the request document.
- Webhooks return 5xx on processing failure, use a durable inbox and recover claims stuck in `processing` for more than five minutes.
- Outbox jobs have exclusive leases, stable dedupe keys, exponential retry and terminal failure after ten attempts.
- Ad payload email is SHA-256-normalized before the retrying outbox is written. Completed delivery payloads are immediately redacted. Full card data is never handled.
- Provider inboxes persist only event metadata plus a payload SHA-256 digest, never the raw Stripe, Play, or Apple notification. Operational errors are centrally stripped of emails, bearer tokens, API keys, webhook secrets, and private-key blocks before logs or retry records.
- Cloud paths are UID-scoped; clients may address only the fixed `save0` through `save20` slots. Signed URLs expire after ten minutes and target staging objects only; upload size and SHA-256 are checked before a create-only immutable revision is copied and committed to the manifest. Each slot retains the current plus three prior revisions. Pruned revisions are deleted immediately when possible and otherwise by a leased, retrying worker that refuses every path outside the exact immutable-revision namespace or belonging to a different job UID. An administrator can audit and requeue only terminal failures without receiving UID-bearing paths. `CLOUD_SAVE_CLEANUP_ENABLED` defaults to `false`.
- Cloud-storage monitoring persists only aggregate object/byte counts and dated growth. Bucket paths and SDK error bodies are never written to monitoring documents or returned to Admin; monitoring and cleanup record generic failure states because provider errors can contain UID-bearing object paths. Admin receives only cleanup counts by state. `CLOUD_STORAGE_MONITORING_ENABLED` defaults to `false`.
- Firestore and Storage client rules deny everything. Service-account and provider credentials belong only in Netlify secrets.
- A present browser `Origin` is rejected unless it is an approved WonderLang, staging, or Android WebViewAssetLoader origin; native clients that do not send `Origin` remain supported. CORS headers are not treated as authorization.
- Netlify applies a coarse IP/domain edge limit, while Firestore transactions apply independent per-account limits to checkout, billing portal, legacy claims, store receipt claims, account-security operations, cloud reads/writes, and administrator reads/writes. Rate-limit document IDs contain only one-way hashes, and a limiter failure rejects the protected request.
- Firebase App Check verification is implemented for authenticated account and administrator APIs. `APP_CHECK_ENFORCEMENT_ENABLED` defaults to `false` and must remain off until every supported web, Android, iOS, and desktop client can attach a valid `X-Firebase-AppCheck` token.
- Subscription reconciliation has an exclusive Firestore lease, bounded provider concurrency, sanitized operational errors, and per-subscription backoff. It calls only Stripe retrieve, Google Play subscription get, and Apple subscription-status APIs; it never acknowledges, cancels, refunds, or changes billing-provider state. `SUBSCRIPTION_RECONCILIATION_ENABLED` defaults to `false`.

The audited account-deletion workflow is implemented with recent-login confirmation, immediate session revocation, a 30-day recovery window, and a separately disabled purge worker. Firestore deletion tests cover pseudonymizing linked ledger/order rows, removing internal buyer-email copies, canceling unfinished personal side effects, and deleting cloud paths. Provider-mocked tests cover clearing only Google Sheet email cells and issuing MailerLite GDPR forget requests without persisting provider response bodies. Before production: run one explicitly approved external deletion canary, approve minimized-ledger retention, provision App Check for every supported client and then enable its enforcement switch, configure platform-level Netlify log redaction, restrict service-account IAM, rotate credentials after migration, and commission an external review of auth linking and store receipt replay cases.
